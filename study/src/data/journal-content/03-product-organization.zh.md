这混乱的两周、让我想了很多东西。

一开始我只是想把手上的原型做好，把交互逻辑捋顺，把产品展示得更完整一点。但是在不断修改的过程中，我越来越感觉到一个问题：很多时候，设计上的问题其实不是设计问题。

如果一个产品最开始没有想清楚自己的形态，后面的设计会变得非常痛苦。

因为每增加一个业务，就像是在原来的结构上不断打补丁。今天加一个入口，明天加一个页面，后天发现用户路径不合理，然后再重新调整。

设计师就会陷入一种不断返工的状态。

我越来越意识到，设计师做原型真正困难的地方可能不是界面，而是界面背后的逻辑。

一个产品为什么这样组织？

用户为什么从这里进入？

不同任务之间是什么关系？

未来新增业务之后，这个结构还能不能继续生长？

这些问题如果没有想清楚，最后落到设计层面，就是无穷无尽的修改。（PS这里我很想翻白眼🙄我们的产品经理是团队里最了解业务的人，但“懂业务”和“做产品”其实是两件事情。懂业务更多是知道客户现在需要什么，知道这个项目怎么推进，知道当前的问题怎么解决；但做产品还需要有另外一种能力，就是从具体需求里抽象规律，思考这个产品未来应该长什么样。可是现实是小团队里资源有限，一个人往往需要同时承担很多事情，要沟通客户、推进项目、跟进开发、解决各种突发问题。长期处在这种多线程状态下，其实很难留出完整的时间去思考产品形态。这里白眼收回🙄现在的困难不是某一个人的能力问题，而是组织结构本身的问题。当所有人都被业务推着往前走，每个人都在解决眼前的问题，但很少有人能够停下来问一句，这也是为什么我后来越来越觉得，小公司和大厂最大的区别可能不仅仅是资源，而是有没有这样的空间和机制，让人可以脱离具体任务去思考长期方向。小公司的优势是每个人都可以参与很多事情，设计可以参与产品讨论，工程可以影响产品形态，但代价就是每个人也更容易被大量具体事务淹没。现在回头看，我对这件事的感受其实也比较矛盾，一方面我会因为产品形态没有提前确定而焦虑，觉得很多返工本可以避免；但另一方面，我也能理解身处这个位置的人为什么会这样，因为当一个人每天都在处理大量事情的时候，思考本身就变成了一种奢侈。🙄🙄🙄）

这段时间我对我们产品形态也有过一次比较大的调整。

入职之前的产品更接近传统 SaaS 产品。

不同的数字同事对应不同的工作空间。

比如用户想做肿瘤报告，就进入肿瘤报告 workspace；想做报价，就进入报价 workspace；想做审核，就进入审核 workspace。

这个逻辑其实没有错。

但是后来我重新思考了一下我们的用户。

我们的服务对象并不是一个只完成单个任务的个人。

更多时候，他们属于一个组织。

一个企业里面可能同时存在很多项目，而一个项目下面又包含很多不同任务。

比如一个药效研究项目，可能同时涉及报告撰写、报价方案、质量审核，甚至后续还有更多协作流程。

所以我后来把产品结构调整成了“项目-任务”的形式。

项目作为一个大的上下文，下面承载多个任务，每个任务再调用不同的数字同事。

这个变化让我觉得比较重要。

因为它改变了我对于 Agent 产品的理解。

以前更像是在业务流程里面增加 AI。

比如原来的工作流是什么样，然后想办法让 AI 去提升其中某一个环节。

但是现在我觉得，也许 AI 原生产品应该反过来。

不是在业务上生长 AI，而是在 AI 的逻辑上重新组织业务。

当然，这个想法现在也还只是一个探索，我不能确定它一定是正确答案。

但是至少它让我觉得，产品不应该只是能力的堆叠。

还有一个比较强烈的感受，

AI 产品的 Dominant Design，也就是相对稳定的主导形态，还没有真正形成。

用一个不完全严谨但比较好理解的比喻：福特T型车出现之前，汽车可以长得像马车、也可以像蒸汽机车，各种形态都有人尝试。直到T型车把"四轮+内燃机+流水线"固定下来，大家对汽车的想象才收敛。

而现在的 AI 产品还处在比较流动的阶段。

Chatbot 可以成立，Canvas 可以成立，节点拖拽可以成立，左右分栏也可以成立。很多形态单独看都能自圆其说，但还没有一种形式能够覆盖所有业务。

所以我觉得我们的产品需要同时存在两部分。

一部分是工作的基本外壳：

这套基本结构最好保持固定，因为用户需要一个稳定的认知模型。

另一部分应该保持开放、允许生长和变化。

我最近关注到腾讯 WorkBuddy打通了腾讯文档。这其实是一个to B化改造的亮点，用户可以在同一个 Agent 任务文档里完成在线编辑，分享和多人协同，同时某种意义上也是多 Agent 协作。对于腾讯来说，这是成熟产品生态之间的连接。

类似地，飞书并入豆包，豆包企业版目前也在打通飞书的企业知识和协作工具，能够在授权范围内调用飞书文档、表格、日历等能力，并交付可以继续编辑和协作的结果。这种“大模型入口加成熟协作生态”的组合，我觉得确实是 AI ToB 很值得观察的一种范式。

但这同时也是一个提醒，我们不能简单复制大厂的产品形态。

腾讯已经有腾讯文档、企业微信和微信，字节已经有飞书及其文档、表格和组织体系。它们去做在线编辑和多人协同，本质上是在打通已有成熟产品。

我们目前不具备相同的生态条件。如果投入很大成本重新做一套在线文档编辑器，很可能是一件投入很重、但无法形成优势的事情。

所以我目前比较倾向于：

我们的主操作区仍然落在 Chatflow。

右侧可以负责预览、证据、产物和必要的轻量操作，但没有必要在现阶段发展成一套完整的在线工作套件。

我们的差异化更应该落在：

对医药业务的理解；

数字同事的专业能力；

对业务文件和上下文的处理；

专业审核流程；

数据、任务与产物之间的可追溯关系。

也就是不和大厂竞争通用办公生态，而是把垂直行业的 Agent 做得更专业、更可信。

另外一个让我思考比较多的问题，是 Agent 能力本身如何产品化。

现在很多时候，我们讨论 AI 产品，会关注界面。

但是实际上，一个 Agent 产品真正的核心，可能不是 UI，而是背后的能力链。

但是目前我感觉，我们对于这些东西还没有形成特别清晰的方法论。

技术更多是在不断尝试新的实现方式。

产品更多关注业务需求。

设计则负责最后的呈现。

但中间缺少一个真正把 Agent 能力转化成产品体验的人。

这也是我觉得未来比较想补充的方向。

所以最近我给自己列了一些之后想做的事情。

第一件事情是学 Python。

不是为了成为纯开发，而是因为我觉得在 AI 时代，单纯依赖自然语言去修改代码是不够的。

AI Coding 很强。

但是如果完全看不懂代码，遇到问题的时候其实还是非常被动。

至少需要具备阅读代码、理解结构、简单 Debug 的能力。

第二件事情，是系统学习 Agent 产品化。

包括 Agent 的架构、工具调用、Memory、RAG、Workflow，还有类似 HANA、Trace 这种过程可视化。

第三件事情，是学习自动化评测，也就是 Eval。

因为未来 AI 产品一定不能只靠人工体验判断好不好。

如何评价一个 Agent 的能力，会成为非常重要的一部分。

第四件事情，是希望自己可以在 GitHub 上做一些完整项目。

不是只做前端，也不是只做视觉。

而是尝试完成一个完整闭环。

我觉得现在 AI Coding 降低了执行成本，真正重要的是能不能提出一个完整的问题，然后把它实现出来。

这段实习还有一个让我比较深的感受，是关于组织。

最近公司里面有大规模的人员流动，有人离开（非常多人离开），也有人加入（非常多人加入），我对于这种变化其实有一点不适应。

因为这是我第一次比较近距离地感受到，一个真实的组织并不是学校里那种相对稳定的集体。

在学校里，一个班级、一个社团，大家一起经历一段时间，人的离开往往会留下比较明显的痕迹。但进入公司之后，我第一次发现，组织对于人的流动有一种很强的消化能力。

一个人在这里工作了一段时间，投入了很多精力，和很多人合作，最后离开。

可能过几天，新的任务依然会继续推进，新的同事会加入，大家也会继续开新的会议。

对于离开的人来说，这可能是一段痛苦经历。

但是对于留下的人来说，随着时间推移，这件事情可能很快就会被新的工作覆盖。

这让我产生了一种很奇怪的感觉。

有一点像是人在组织中被某种程度上“抽象化”了。

大家当然不是没有感情，只是当一个组织运行时间足够长之后，人的流动会逐渐变成一种日常现象。

今天是某个人离开，明天可能又是另一个人。

久而久之，人会产生一种保护机制，让自己不要投入太多情绪。

因为如果每一次离开都产生巨大的情绪波动，组织可能根本无法运转。

但对我来说，这次经历其实很珍贵。

因为这是我第一次亲身感受到这种变化。

作为一个刚进入职场的人，我还没有经历过很多次人员流动，所以我仍然会对一个人的离开产生真实的感受。

我会想：

一个曾经参与过这些事情的人，就这样离开了。

他的经验、他的努力、他的想法，也许以后不会再继续参与这个组织的未来。

而几年之后，当我经历更多这样的事情，也许我也会慢慢习惯。

一方面，我理解组织为什么需要这样运行。

企业需要效率，需要不断调整，需要根据业务变化重新分配资源。

但另一方面，我也觉得，人不能完全被看成组织里的一个变量。

一个人的价值，不应该只由他当前能创造多少产出决定。

现代组织的问题不是没有人情，而是系统运行久了之后，人很容易被简化成一个角色、一份职责、一段经历。

可能今天离开的是别人，但某种意义上，也是提醒未来的自己：

不要因为习惯了组织规则，就忘记了每一个坐在你旁边的人，实际上都是一个完整的人。

我觉得这也是我第一次进入职场后，一个比较重要的感受。

以前我更多关注事情能不能做好，能力能不能提升。

但现在我开始意识到，组织不仅仅是一套流程和分工，它也是很多具体的人，在有限的时间里共同经历一些事情。

最后，如果让我总结这段时间最大的变化。

可能不是我学会了多少工具。

也不是我做了多少页面。

而是我开始意识到，很多事情没有标准答案。

产品没有。

设计没有。

组织也没有。

很多时候，我们只能在不断变化的环境里，建立自己的判断。

我现在也没有确定未来一定要做什么岗位。

可能是设计。

可能是产品。

可能更靠近 product engineering或者design engineering。

但是我确定的是，我希望自己不要只停留在执行一个已经确定的问题。

我更想知道：

这个问题为什么存在。

它应该怎么被定义。

以及有没有可能创造一个更好的答案。
